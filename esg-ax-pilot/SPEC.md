## 0. Claude Code 작업 원칙 (반드시 준수)

1. 한 번에 전체를 만들지 않는다. **8장 개발 단계 순서대로, 지시받은 단계만** 구현한다.
2. 각 단계가 끝나면 테스트를 실행하고, 무엇을 만들었는지와 다음 단계에서 확인이 필요한 사항을 요약한다.
3. 요구사항이 불명확하면 추측해서 크게 만들지 말고 질문하거나, 가장 단순한 형태로 만들고 가정을 `docs/assumptions.md`에 기록한다.
4. **LLM은 판정과 근거 작성만 한다. 점수 계산, 상태 변경, 메일 발송은 반드시 일반 코드가 한다.**
5. **실제 메일 발송 금지**(운영 전환 승인 전까지). 모든 메일은 `outbox` 테이블에 저장만 하고 화면에서 미리보기만 한다(dry-run).
6. API 키 등 비밀값은 `.env`로만 관리하고 코드·로그에 남기지 않는다.
7. **실제 협력사명이 들어 있는 원본 데이터는 저장소에 커밋하지 않는다.** `data/input/`은 git 제외.

## 1. 프로젝트 개요

### 1.1 배경 — 내재화
- SK텔레콤(원청사)은 지금까지 공급망 ESG **자가진단 검증**과 **개선 컨설팅**을 외부 업체(Click ESG 플랫폼 운영사)에 맡겼다.
- **내재화**: 이 업무를 SKT 직원이 직접 수행한다. **Click ESG 플랫폼은 앞으로 쓰지 않는다.**
- 담당자와 협력사가 익숙하므로 **업무 흐름은 Click ESG를 그대로 따른다**(3장).
- 적은 인원으로 외주와 같은 품질을 내기 위해 **AI Agent가 검증·컨설팅의 반복 업무를 먼저 처리하고, SKT 담당자가 최종 판단**한다.

### 1.2 목표
- **실제 업무에 사용한다**(시연용이 아님). 품질·추적성·확장성을 우선한다.
- 규모: **2030년 ESG 진단 500개사, ESG 컨설팅 250개사** (2024년 진단 106개사).
- 지표·검증 기준은 Click ESG 데이터(2024, 66개 정성지표)를 우선 반영하고, **2027년 개편**에 대비해 지표 체계를 버전별로 교체 가능하게 만든다.

### 1.3 범위
| 구분 | 내용 | 시기 |
|---|---|---|
| **핵심** | ④ 검증 (증빙 스크리닝, 점수 제안·확정, 검토의견 초안), ⑤ 컨설팅 (개선과제·BP 매칭, 개선계획 적정성 검토 보조) | 이번 개발 |
| 기반 | 지표 마스터·버전, 점수 계산, 상태 머신, 담당자 화면, 과거 Click ESG 데이터 적재 | 이번 개발 |
| 보조 | 운영 Agent: 증빙 보완·개선계획 요청 메일 초안, 지연 점검 | 이번 개발 (축소) |
| 추후 | **협력사용 웹사이트**(가입, 자가진단 입력, 증빙 업로드, 개선계획 제출) | 별도 단계 (8장 10단계) |
| 추후 | 사내 서버 배포, SSO, 실제 메일 발송, 보안 검토 반영 | 실제 사용 시점 |

- 협력사 웹사이트는 나중에 만들지만, **같은 DB·같은 상태 머신에 붙도록** 지금부터 설계한다. 그 전까지 협력사 응답은 **엑셀 적재**로 받는다.

## 2. 기술 스택

- Python 3.11+
- LLM: Anthropic Claude API
  - 기본 모델: `claude-sonnet-5-5` (판정·매칭·의견 초안)
  - 단순 분류·요약: `claude-haiku-4-5-20251001`
  - 모델명과 호출 환경(직접 API / 사내 클라우드 경유)은 `config.py` 한 곳에서 관리
- Agent 구현: Anthropic Python SDK의 tool use (구현 전 최신 공식 문서 확인)
- DB: SQLite(개발) → **PostgreSQL(운영)**. SQLAlchemy로 양쪽 모두 동작하게 한다.
- 담당자 화면: Streamlit (내부용)
- 협력사 웹사이트(추후): 외부 접속용 웹 프레임워크(FastAPI + 웹 화면). 담당자 화면과 같은 DB를 쓴다.
- 파일 처리: pandas/openpyxl(엑셀), PyMuPDF(PDF), **이미지·스캔본은 Claude 이미지 입력으로 판독**, hwp 등은 변환 후 처리 `[TBD: 변환 방법]`
- 테스트: pytest

## 3. 업무 흐름 (Click ESG 준용)

| 단계 | SKT 담당자 | 협력사 | AI Agent |
|---|---|---|---|
| ① 협력사 관리 | 협력사 등록, 진단 대상 설정 | (추후 웹사이트) 가입·등록 동의 | 운영: 요청 메일 초안 |
| ② 기준정보 | 지표 버전·산업별 가중치·산업군(GICS) 적용 | 재무정보 입력 | 진단: 산업군 매핑 제안 |
| ③ 자가진단 | 데이터 등록 요청, 진행 확인, 마감 | 66문항 응답 + 증빙 | 운영: 미입력 점검·리마인드 초안 |
| **④ 검증** | **판정 검토, 최종 점수·검토의견 확정** | (보완 요청 시) 증빙 보완 | **진단: 증빙 스크리닝, 점수 제안, 검토의견 초안** |
| **⑤ 개선 컨설팅** | **개선대상 지표·과제·목표 확정, 계획 적정성 판단** | 개선계획 제출·이행 | **컨설팅: 개선과제·BP 매칭, 계획 적정성 검토 보조** |
| ⑥ 리포트 | 최종 진단 리포트 | 결과 확인 | (Step2) 리포트 초안 |

- Agent 3개는 서로 직접 호출하지 않는다. 공유 DB의 케이스를 읽고 정해진 테이블에 기록한다.
- 오케스트레이터는 **상태 머신 코드**다.
- 사람 확인 지점은 **승인 대기 상태**로 멈춘다.
- 협력사에게 나가는 연락은 **운영 Agent만** 생성한다.

## 4. 상태 머신 (case.status)

| 상태 | 의미 (Click ESG 대응) | 다음 작업 주체 |
|---|---|---|
| `REGISTERED` | 진단 대상 등록 | SKT: 등록 요청 |
| `DATA_REQUESTED` | 데이터 등록 요청 (미입력) | 협력사 입력 / 운영: 지연 점검 |
| `IN_PROGRESS` | 입력중 | 협력사 |
| `SUBMITTED` | 입력완료 | SKT: 마감 |
| `CLOSED_SELF` | 자가진단 마감 (자가진단 점수 산출) | 진단: 증빙 스크리닝 |
| `SCREENED` | AI 스크리닝 완료 → **검증 승인 대기** | SKT 검증 담당 |
| `SUPPLEMENT_REQUESTED` | 증빙 보완 요청 | 협력사 → 다시 `SCREENED` |
| `VERIFIED` | 검증 완료 (최종 점수·검토의견 확정) | 컨설팅: 개선과제 도출 (대상인 경우) |
| `IMPROVEMENT_PROPOSED` | 개선과제 제안 → **확정 대기** | SKT 컨설턴트 |
| `PLAN_REQUESTED` | 개선계획 요청 | 협력사 제출 |
| `PLAN_SUBMITTED` | 개선계획 제출 → 적정성 검토 | 컨설팅 보조 + SKT |
| `MONITORING` | 이행 점검 | 운영 |
| `DONE` | 종료 | - |

- 컨설팅 대상이 아닌 케이스는 `VERIFIED` → `DONE`.
- 반려 시 이전 상태로 되돌리고 사유를 기록한다.
- 모든 상태 변경은 `audit_log`에 남긴다(누가, 언제, 무엇을, 이전/이후 상태).

## 5. 평가 체계 (Click ESG 준용, 규칙 코드로 계산)

- **지표 수준**: 지표마다 수준별 선택지와 점수를 정한다: **0 / 3 / 7 / 10점** (지표에 따라 일부 수준만 사용).
- 협력사가 **자가진단**으로 수준을 고르고 → AI가 증빙으로 적정성을 확인해 **제안** → **컨설턴트가 최종 수준을 결정**한다.
- 지표 점수 → 중분류 점수(지표 평균) → 영역 점수(중분류 × 산업별 가중치, 합계 100) → 종합 점수(10점 만점)
- 위험등급: 고위험 0~2.99 / 중위험 3~6.99 / 저위험 7~10. ESG 경영등급 RM-1~RM-7 `[TBD: 구간]`
- 위반 관련 6개 지표(환경법규·근로기준법·정보보호·분쟁광물·윤리경영·공정거래)의 점수 반영 방식 `[TBD]`
- 선택지·점수·가중치·등급 구간은 **지표 버전**(`2024-ClickESG`, 이후 `2027` 등)에 묶어 설정 파일/DB로 관리한다.

## 7. Agent별 상세

### 공통 규칙
- 모든 Agent 출력은 **JSON 스키마로 검증**한다(pydantic). 실패 시 1회 재시도, 그래도 실패하면 `확인필요`.
- 모든 판정에는 **근거(파일명, 쪽 또는 문항, 원문 요약)**가 있어야 한다. 근거 없는 판정은 저장하지 않는다.
- 시스템 프롬프트는 `prompts/`에 둔다. 지표 마스터·검증 가이드처럼 반복되는 긴 문서는 프롬프트 캐싱을 적용한다.
- 대량 처리(500개사 × 66지표)는 **Batch 처리 옵션**을 둔다.

### 7.1 진단(검증) Agent (`app/agents/diagnosis/`)

**모듈 A — 검증 우선순위 (Risk Tier)**
- 산업군·자가진단 점수·응답 패턴으로 먼저 볼 협력사를 정한다. 규칙은 코드, 애매한 경우만 LLM 보조.

**모듈 B — 증빙 스크리닝 (핵심)**
- 지표별 점검: ① 증빙 필요 지표에 증빙이 있는가 ② 증빙이 선택한 수준을 뒷받침하는가(범위·대상·내용) ③ 기준일에 유효한가 ④ 응답 간 모순이 있는가
- 출력: `findings`(판정·근거·**제안 수준**·확신도). 제안 수준은 해당 지표의 선택지 중에서만 고른다.
- 완료 후: `SCREENED`. 담당자가 지표별로 승인·수정하면 `verified_responses`에 저장, 점수는 코드가 재계산.

**모듈 C — 검토의견 초안**
- 확정된 검증 결과로 총평·영역별 의견 초안 작성. 문체는 과거 검토의견 샘플을 따른다 `[TBD: 샘플]`. 확정은 담당자.

### 7.2 컨설팅 Agent (`app/agents/consulting/`)
- 입력: 검증 점수, findings, 개선대상 지표(규칙 코드가 선정), `best_practices` `[TBD]`
- 처리: 개선과제 도출 → 업종·지표에 맞는 BP 매칭(없으면 "매칭 BP 없음", 지어내지 말 것) → 우선순위·목표 수준 제안
- 개선계획 적정성 검토 보조: 협력사가 낸 계획이 과제·목표에 맞는지 근거와 함께 제안
- 확정은 SKT 컨설턴트.

### 7.3 운영 Agent (`app/agents/operations/`, 보조)
- 증빙 보완 요청, 개선계획 요청, 리마인드 메일 초안 (`outbox`, dry-run)
- 기한 초과·승인 대기 지연 점검 (일반 코드, LLM은 요약 문장만)

## 8. 개발 단계

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| 1 | 프로젝트 골격, config, DB 모델, 샘플 데이터 | ✅ 완료 |
| 2 | **지표 마스터·버전** + Click ESG 과거 데이터 적재 (컬럼 매핑은 설정 파일) | 2024 데이터 106개사 × 66지표 적재, 선택지·점수표 자동 추출 |
| 3 | 상태 머신 + audit log | 4장 전이 테스트 통과 |
| 4 | 점수 계산 (지표→중분류→영역→종합, 등급) | 2024 데이터로 Click ESG 점수 재현 |
| 5 | 증빙 파일 변환 (PDF·이미지·엑셀 등 → 판독 가능한 형태) | 샘플 증빙 형식별 변환 성공 |
| 6 | 진단 Agent 모듈 B (증빙 스크리닝) + 모듈 A | 샘플 증빙으로 판정·근거·제안 수준 생성 |
| 7 | 담당자 검증 화면 (지표별 승인·수정·반려, 점수 변화) | 승인/수정으로 점수·상태 변경 |
| 8 | 진단 Agent 모듈 C (검토의견 초안) | 확정 케이스에 의견 초안 생성 |
| 9 | 컨설팅 Agent (개선과제·BP, 계획 적정성 검토 보조) | 검증 완료 케이스에 개선과제 생성 |
| 10 | 운영 Agent (보조) | outbox 초안 생성·승인 |
| 11 | 품질 평가 (외주 판정과 비교) | 평가 리포트 생성 |
| 12 | 협력사 웹사이트 (추후) | 가입·자가진단 입력·증빙 업로드·제출 |

## 9. 보안·데이터 원칙

- 실제 협력사 데이터는 `data/input/`에만 두고 커밋하지 않는다. 샘플·테스트는 익명화본을 쓴다.
- 외부 API 전송 범위·호출 환경은 **실제 사용 시점의 보안 검토**에 따른다 `[TBD]`. `config.py`에서 교체 가능하게 한다.
- 로그에 원본 증빙 내용 전문을 남기지 않는다.

- 협력사 1곳당 비용을 산출해 외주 단가와 비교할 수 있게 한다.
